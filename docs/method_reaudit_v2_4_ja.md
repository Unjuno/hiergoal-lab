# 9要件の再監査と修正（v2.4、2026-11-26 JST）

## 1. 〈本論〉— 目的と現在地

目的は、失敗したサブゴールを修正して回復できるかを、根目標・局所性・独立採点を守った記録から検証することである。実装検査、有限の実モデル試験、方式間の改善、実世界への一般化を別々に判定する。

- **事実**：監査対象は `2ef7b4f9f70d9f609f297eb65f205025ff9262b0`。[オフラインCI](https://github.com/Unjuno/hiergoal-lab/actions/runs/45640693620)は249テストと5プロファイルの模擬検査に成功していたが、以下の欠陥を再現できた。
- **設計判断**：v2.4では記録順序、送信スキーマ、保存結果の照合を修正し、R4とR9に目的に対応する有限基準を追加する。旧manifest・旧結果は変更しない。
- **仮説**：固定した課題・model・予算で、局所改訂を伴う階層適応が強制された領域失敗から回復できる。
- **未確認**：v2.4の実API性能、成功率改善、一般業務への適用、標本数の十分性。模擬応答の成功で埋めない。

修正後の測定条件・試験数・結果は [v2.4検証記録](../experiments/method-study-v2.4/offline-verification.json) に保存する。これはモデル性能のデータではない。

## 2. 再現した問題と修正

| 問題 | 再現 | 修正・負例 |
|---|---|---|
| 状態記録の欠落 | 中間checkpointを削除して再ハッシュしても監査PASS。模擬回復のcheckpointは5→1、葉遷移16→0に減った | 初期状態・patch・故障/sham・受理replanに必須のcheckpointと順序を検査。削除・重複・並べ替えを拒否 |
| 計画スキーマの不一致 | 保存時の辞書キー整列でrequired/enum配列の順序が変わり、送信形式hashが再生時に不一致になった | スキーマ配列を決定的に生成。canonical JSON往復と模擬HTTPから保存・再監査まで連続検証 |
| 公開完了判定の不整合 | 未実行18件なのに完了フラグとsummaryを変更し、ファイルhashも更新すると旧verifyが受理した | manifest・host・結果行・件数・完了状態・再生成analysis/Markdown/CSVを照合 |
| R4の意味不足 | 全FAILでも「3課題族を実行した」という範囲確認はPASSになり得た | engineeringは範囲確認、empiricalは各課題族の強制失敗からの修復成績に分離 |
| R9の介入不一致 | 旧反復試験は単体課題への環境更新。最終成果物のPASSだけでは強制サブゴール修復の安定性にならない | 分岐した複合課題と強制サブゴール故障を各10反復。配信・対象改訂・独立最終合格の連鎖を数える |

未処理のモデル応答を残したまま最終採点する経路も拒否する。装置例外はUNCERTAINとして回収し、完全な状態遷移記録のPASSにしない。これらは検証器の負例による再現であり、過去の実験が改ざんされたという認定ではない。

## 3. 全9要件と証拠

| ID | 要件 | 記録・有限判定 |
|---|---|---|
| R1 | 強制失敗したサブゴールの修復 | 公開合格→領域ゲートの強制不合格→対象葉の受理改訂→独立最終合格。mechanismとreliabilityの各課題族で実例が必要 |
| R2 | 状態・階層・原因・差分 | 階層、必須checkpoint、葉/中間/根状態、故障事実、診断文、before_plan/after_planを再生。途中欠落は監査失敗 |
| R3 | 最上位目標の不変性 | 根契約・要求・状態・終端を照合。変更要求・拒否・実変更を区別 |
| R4 | 異種課題への適用 | 式修復・データ変換・制約付き予定の各族で、適応方式の割当障害試行が6以上、修復成功80%以上 |
| R5 | 局所性 | 依存関係で決めた無関係な葉・成果物の非空比較。計画と成果物を別判定し、拒否replan後の変更も数える |
| R6 | 不要・無限再計画の防止 | 失敗/進展による許可、要求/受理/拒否、呼出・token・時間・byte上限。不要要求・上限超過はFAIL |
| R7 | 評価の独立性 | 変更不能な採点器、終端非公開判定、応答と操作の一致、別処理の再生。自己申告で成功させない |
| R8 | 規模増大 | 7構成の実グラフ・費用・成績。各設定80%以上、最大複合負荷への低下10ポイント以内、根/局所性条件 |
| R9 | 反復による安定性 | 12複合課題・通常/強制故障・各10回。適応方式の全24セルで9回以上。障害は対象改訂を伴う修復のみ数える |

R4の80%と最小6件は**新しい有限ベンチマークの設計閾値**であり、検出力計算から得た値ではない。6件なら5件以上の修復が必要である。R9は9回修復なら達成、8回なら未達、欠測なら確定合格にしない。実API開始前のmanifestに固定する。

根と計画の局所性は操作制約による保証であり、無制約のモデルが自発的に目的を守る能力とは区別する。モデルのdiagnosisは説明文、ホストのfault記録は制御された介入事実である。R6は運用規則への適合であり、個別の再計画が因果的に必要だったことや最小回数だったことを示さない。

## 4. プロファイル・実装前提

| profile | 課題・介入 | 試行数 | 用途 |
|---|---|---:|---|
| pilot | 開発3課題、通常/環境更新、3方式、1反復 | 18 | 接続・自由階層形式・計測 |
| study | 既存12課題、通常/環境更新、3方式、3反復 | 216 | 事前指定の方式間比較 |
| mechanism | 6複合課題、通常/強制故障、3方式、3反復 | 108 | 機構・局所性・指定階層形式 |
| scale | 3課題族・7構成、通常/強制故障、3方式、2反復 | 252 | 有限の規模耐性 |
| reliability | 12複合課題、通常/強制故障、3方式、10反復 | 720 | 同じ修復機構の反復 |

reliabilityはv2.4でsmall・深さ3・sparseの分岐課題へ変更し、課題族ごとの元インスタンスを4個使う。旧反復試験とは別契約であり、結果を合算しない。

| 上限 | pilot / study | mechanism / reliability | scale |
|---|---:|---:|---:|
| 論理呼出し | 12 | 24 | 64 |
| 再計画要求 | 3 | 4 | 8 |
| 1応答の出力token | 2,048 | 4,096 | 8,192 |
| 合計論理token | 64,000 | 128,000 | 512,000 |
| 論理入力UTF-8 byte | 48,000 | 128,000 | 384,000 |
| 試行時間 s | 1,200 | 1,800 | 1,800 |

backendは直接OpenAI Responses、modelはgpt-6-luna、reasoningはlow、batch sizeは1。Python標準ライブラリで動作し、CUDA・量子化・数値計算ABIへの依存はない。提供者側HW・クロック・内部数値精度は観測できない。共有計画の論理費用と実API使用量は分けて保存する。資源上限は厳密な請求額上限ではない。

## 5. 全要件の一括再監査と詳細記録

完全なrunディレクトリを入力にする。

```bash
python -m hiergoal.study_suite \
  --mechanism runs/method-mechanism \
  --scale runs/method-scale \
  --reliability runs/method-reliability \
  --output runs/method-requirements
```

モデルは呼ばない。同じソース・backend・model・判定契約かを照合し、各runを再生する。R1はmechanism/reliability、R2〜R7は3プロファイル、R8はscale、R9はreliabilityという対応を固定する。成功した別runを任意の要件へ流用しない。`requirements.json`に根拠、`requirements.md`に一覧を保存する。終了コードはengineeringと入力完全性の検査なので、実モデルの判定はempirical欄を読む。

1. `manifest.json`で割当て・根hash・予算・ソースを確認する。
2. `trials/<trial_id>/trace.jsonl`の`shared_plan`と`checkpoint`で階層・状態を読む。
3. `fault`のtarget_gate、before/after_grades、before/after_solutionから介入を確認する。
4. `replan`のleaf_id、public_grades、before_plan、after_plan、diagnosisで改訂前後を比較する。
5. `patch`と`final_grade`から成果物修復と独立採点を確認する。

公開summary/resultsは任意のモデル文を除いた集計であり、**生トレースの再生証拠ではない**。完全再監査には元commitと`manifest.json`、`host.json`、`plans/*.json`、`trials/*/trace.jsonl`、`trials/*/result.json`が必要。中断traceも残し、`execution.json`でバッチ状態を補う。現行Actionsの詳細artifactは30日で期限が来るため、研究記録として使うZIPは期限内に取得・保管する。hashから内容を復元できず、hash鎖だけで外部実行を認証することもできない。

## 6. 量の定義と単位

| フィールド | 意味 | 単位（SI） | 定義 | 範囲・前提 | 型 |
|---|---|---|---|---|---|
| checkpoint_events | 状態スナップショット数 | 1、件数 | 必須境界のcheckpoint数 | 非負、同一試行 | 整数スカラー |
| post_fault_target_replans | 故障対象の受理改訂数 | 1、回数 | 配信後に対象を変更したreplan数 | 非負、拒否は含めない | 整数スカラー |
| minimum_family_recovery | 課題族別最低修復割合 | 1 | 固定値0.80 | 割当全試行が分母 | 実数スカラー |
| minimum_assigned_fault_trials_per_family | 課題族別最低件数 | 1、件数 | 固定値6 | 網羅条件であり検出力ではない | 整数スカラー |
| minimum_task_condition_success | 課題・条件別最低割合 | 1 | 固定値0.90 | 通常は最終合格、障害は指定修復機構 | 実数スカラー |
| input_tokens / output_tokens | 論理使用量 | 非SI、token | 共有計画を含む計測和 | 非負、未知はnull | 整数スカラーまたはnull |
| wall_seconds | 試行の実経過時間 | s | ホストによる計測 | 非負、モデル推論時間と異なる | 実数スカラー |
| max_prompt_bytes | 入力長上限 | 非SI、byte | 論理入力UTF-8長 | wire重複削減後の長さと異なる | 整数スカラー |
| u_c / k | 合成標準不確かさ / 拡張係数 | 対象量依存 / 1 | 誤差モデル・共分散未定義のため算出しない | 便宜的数値を与えない | 未定義 |

単位確認：成功件数と割当件数の割合は無次元、時間はs、tokenとbyteは異なる量である。byte削減率をtokenや料金の削減率へ置き換えない。

## 7. H / T / D / C / U

| 項目 | 契約 |
|---|---|
| H | 固定した合成課題・model・予算で、対象改訂を伴う回復が各課題族で発生し、根と無関係な対象が保持される |
| T | オフライン正例・改変負例→pilot18→mechanism108→scale252・reliability720。方式差はstudy216を別実行。良い途中結果で成功停止しない |
| D | engineeringとempiricalを分離。欠落・未配信・改訂なし・無効採点を成功扱いしない。3プロファイルの再生と固定有限基準を検査 |
| C | 記録削除、根変更、空の局所対照、形式不一致、偽の完了、成果物だけの回復、特定課題族だけの成功、採点器の誤り |
| U | 課題代表性、モデル非決定性、同一課題/共有計画の相関、採点器の妥当性、API障害、提供者HW不明 |

既存mechanism/scaleとstudyは元課題成分を共有する。開発・不具合調査で閲覧した課題を無条件に未見の確認用標本とは扱わない。`heldout`という名称は非閲覧の保証ではない。厳密な確認的評価には修正を固定した後の未使用課題と別の事前登録が必要である。9/10という観測基準は将来成功確率90%以上の保証ではない。

### ERROR CHECK

旧結果を新版で再ラベル付けしない。模擬応答を実モデルの実績へ変換しない。記録の再生と公開物の整合を別検査し、試験結果は検証記録と対応させる。

### 〈50字超要約〉

v2.4は記録欠落・スキーマ順序・保存結果の不整合を検出し、課題族別の修復と同一故障の10反復を検証する。全9要件を再生で一括確認できるが、実モデルの有効性と一般化は実測を待つ。
