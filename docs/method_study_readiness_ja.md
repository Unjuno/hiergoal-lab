## 2. 実施した検証

| 検証 | 結果 | この結果が意味すること |
| --- | --- | --- |
| 全回帰テスト | 170件成功、16.985 s | 既存90件と追加80件のソフトウェア検証 |
| 本実験の全行程 | 216件の模擬試行が実行・独立採点・再生監査を通過 | 全課題・条件・方式・反復を処理できる |
| 持続する環境変更 | 模擬障害108件の変更と、その後の採点を検証 | 発火・影響・回復の記録経路を検査した |
| 実験未実行の集計 | 216件すべて `NOT_RUN`、方式の優位性と実現可能性は `UNCERTAIN` | 準備だけを研究成功と誤表示しない |
| HTTP要求形式 | モックで要求内容、使用量、エラー、モデル変更を検査 | 本番API接続成功を主張するものではない |
| CI定義 | YAML構文と、手動 `run` だけに認証情報を渡す条件を検査 | push/default prepareで推論要求を開始しない |
| Python・シェル構文 | コンパイル、既存セットアップスクリプトの構文検査成功 | 配布コードの基本的な実行準備 |

測定環境はPython 3.12.14、Linux x86_64、AMD EPYC 9V74、利用可能論理CPU 9、
観測クロック約2,596.15 MHz、RAM 10,451,427,328 byte、逐次実行・batch size 1。
上記の16.985 sはローカル回帰テスト1回の実行時間であり、モデルの性能ベンチマーク値ではない。
提供者側のモデル用ハードウェアやクロックは観測していない。

オフライン参照応答は正解を持つ検査用実装である。したがって、216件の成功や108件の模擬回復から、
LLMの成功率、局所再計画の効果、他の課題への一般化を推定してはいけない。
模擬結果の方式優位性判定は意図的に `UNCERTAIN` のままとした。

## 3. 特に検査した誤判定

- 不正なJSON、未知ゲート、循環依存、最上位目標の書換え、成功の自己申告を受理しない。
- 古い環境・成果物への採点や、依存元変更前の完了状態を流用しない。
- 固定方式と適応方式が同じ初期計画を使い、局所改訂で無関係な計画条件を変えない。
- 最終の非公開採点をモデルへ返さず、修正のために繰り返し利用しない。
- 実際の再計画応答と保存された改訂、応答と成果物変更が一致することを再生検査する。
- ログ欠落、方式ラベルの付替え、使用量の不整合、期限超過を成功扱いしない。
- APIタイムアウトや使用量欠測を0 token扱いせず、途中終了は `UNCERTAIN` とする。
- 未開始試行を消さず `NOT_RUN` とし、障害が発火しなかった試行も主要比較に残す。
- 全方式の初期計画・修正・再計画を論理予算へ計上し、実要求使用量とは分ける。
