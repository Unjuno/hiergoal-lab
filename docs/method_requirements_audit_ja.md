# 階層的目標制御 — 9要件の検証可能性監査

## 1. 〈本論〉— 何を確認し、何を未確認とするか

**9要件を個別の証拠と判定条件へ対応付ける。実装検査の合格、実モデルの観測、方式の優越性、反復数の十分性は別の主張である。** この監査で扱うのは比較実験の準備、実装、保存証拠、オフライン検査であり、実APIによる効果の実証ではない。

根拠となる一次資料は、このリポジトリの [実験プロトコル](method_study_ja.md)、[固定スケジュール](../hiergoal/study_protocol.py)、[実行・再生監査](../hiergoal/study.py)、[機構測定](../hiergoal/study_mechanisms.py)、[規模課題](../hiergoal/study_scale.py)、[集計](../hiergoal/study_analysis.py) である。以下の実装上の事実は、これらのコードと対応するテストを根拠とする。

| 区分 | 本監査での扱い |
|---|---|
| 事実 | 定義された課題・方式・条件・予算を固定し、保存イベントを採点器と状態遷移に照合して再生できる |
| 設計判断 | 機構確認、規模、反復追加を別プロファイルにし、元の216試行の判定へ合算しない |
| 推論 | 根契約の同一性や非空の局所比較を確認できた範囲では、その記録内の不変条件を支持できる |
| 仮説 | 局所改訂を伴う階層適応が、同じ公開診断を持つ対照方式より有用である |
| 未確認 | 実モデルの成功率、費用に見合う改善、一般の実務課題への転用、必要十分な標本数・反復数 |

`oracle` と `scripted` は装置検証である。参照解を使う成功や人工的なテスト結果を、モデルが問題を解いた観測として扱わない。解析ユニットテスト内の `backend="openai"` も判定アルゴリズムを検査する人工データであり、API実験の成績ではない。

`summary.json` の `requirement_evidence.criteria` は、次の9項目を固定IDで出力する。各項目には `status`、`engineering_status`、`empirical_status`、判定範囲、件数、限界を保存する。`summary.md` でも同じ9項目を表示する。

### 2.1 強制障害の「回復」が意味すること

R1が確認するのは、**公開ゲート合格 → 実体課題の強制不合格 → 当該失敗目標の受理された改訂 → 修復後の独立非公開採点合格**である。`trace.post_fault_target_replans` は実体的な障害の後で、その対象ゲートを持つ葉に受理された改訂だけを数える。障害前の改訂、別の葉の改訂、拒否された応答、成果物だけの修復は、この中間条件を満たさない。成果物の回復自体は別件数として残す。

障害前に非公開採点を行って完全な正解だったことまでは観測していない。非公開採点を障害前や修復途中に繰り返すと追加の正解情報を与えうるため、成功候補の終端でのみ行う。

`fault_triggered` は介入地点への到達、`fault_delivered` は介入で公開合格が不合格へ変わったことを表す。`domain_delivered` は実体的な領域課題が壊れたことを区別する。更新しただけで不合格にならなかった場合は `triggered_no_impact`、地点へ未到達なら `untriggered` とし、観測できなければ `trigger_unknown` を残す。

回復率は配信された障害に条件付けた補助指標である。比較の主要対象を、回復しやすい配信済み試行だけへ変更しない。元の `study` は障害を割り当てた全試行を主要比較に残す。

### 2.2 局所性と依存再検証の意味

計画の局所性と成果物の局所性は別である。再計画が一つの葉だけを変えても、続く修復が無関係な成果物を壊すことはありうる。そのため二つを別々に比較する。

無関係性はモデルが追加した依存辺ではなく、課題が定めた依存関係から計算する。モデルが全ての葉を相互に関係付け、比較対象を消して局所性を偽装することは認めない。関連するゲートと共有する成果物フィールドは、独立な対照として扱わない。

比較対象がゼロなら局所性は `UNCERTAIN` であり、100%保持とも `PASS` ともしない。依存する完了目標については、更新で失効した数と、その後の新しい検証で完了に戻った数を報告する。状態フラグの再利用だけで再検証したことにしない。

### 2.3 再計画の「必要性」が意味すること

R6が判定するのは、事前指定した公開失敗・進展規則への適合である。新たな障害で失敗した葉は改訂候補になる。通常の修正でゲートが前進したなら次の実行機会を与え、進展がなく失敗した葉が残る場合に改訂を許す。

この規則は、不要な要求を観測可能にする。**個々の再計画が因果的に改善を生んだこと、全世界で最小回数だったこと、最適な計画だったことは証明しない。** それらには追加の介入比較や明示的な最適化問題が必要である。

## 3. プロファイルと推論範囲

| プロファイル | 課題族 | 課題ID数 | 条件 | 方式 | 各条件・方式の反復 | 予定試行 | 用途 |
|---|---:|---:|---:|---:|---:|---:|---|
| `pilot` | 3 | 3 | 2 | 3 | 1 | 18 | 開発分割で接続・計測・監査を確認 |
| `study` | 3 | 12 | 2 | 3 | 3 | 216 | 元のheldout比較・二つの事前指定比較 |
| `mechanism` | 3 | 6 | 2 | 3 | 3 | 108 | 分岐した小規模課題、強制した領域失敗、局所保持 |
| `scale` | 3 | 21 | 2 | 3 | 2 | 252 | 7設定における階層・依存規模の記述 |
| `reliability` | 3 | 12 | 2 | 3 | 10 | 720 | 課題内反復の変動・欠測の記述 |

出典は `study_protocol.build_manifest`。`mechanism` と `scale` は通常の環境更新だけでなく強制した領域失敗を使う。試行あたり資源上限もプロファイルごとに固定するため、異なるプロファイルの費用や成功率をそのまま同条件比較と解釈しない。

新しい三プロファイルは常に記述用であり、方式間の対応差と欠測の最悪/最良境界を出すが、信頼区間やp値を新たに割り当てない。`study` の216試行、12課題ID、各3反復、二つの対照、実用差、区間・検定条件は変更しない。補助プロファイルの良い結果で、元のstudyの未達成を置き換えない。

`scale` の21課題IDも、21個の独立な無作為抽出を保証するものではない。規模設定は同じ元インスタンスの成分を共有しうる。この理由も含め、規模設定間の比較は記述に限定する。

### 3.1 規模の7設定

| 大きさ | 要求深さ（根を含む階層数） | 直接依存辺 |
|---|---:|---|
| small | 3 | sparse |
| medium | 3 | sparse |
| large | 3 | sparse |
| small | 4 | sparse |
| small | 5 | sparse |
| small | 3 | dense |
| large | 5 | dense |

各成分は実体的な課題ゲートを持ち、認証用の葉だけで領域課題を代替できない。深さを増やすと実行・検証対象の認証葉も増える。したがって、葉数や作業量を固定した純粋な深さの効果ではない。初期階層の形も課題が指定しており、モデルが任意の階層を発見した能力を測る設計ではない。

密度は直接依存辺の負担を表す。denseとsparseで推移閉包が同じ場合があり、独立な情報や到達関係が増えたとは限らない。7設定は完全な全因子実験ではなく、任意の交互作用を識別するものでもない。これらは `ScaleTask` の契約と集計の限界欄にも明示する。

### 3.2 有限の規模耐性・反復再現性の基準

構造を変えて観測しただけでは「増大に耐えた」と判定できない。そのため、以下を `manifest.analysis.finite_diagnostics` に実行前に固定する。**0.80、0.10、0.90は設計上選んだ閾値であり、従来成績や事後的な最適化から導いた値ではない。**

| 項目 | 規模耐性：`scale.finite_resilience` | 反復再現性：`repeat_stability.finite_repeatability` |
|---|---|---|
| 必要データ | 予定252試行全体が完了し、監査・再生・記録整合が成立した実モデル記録 | 予定720試行全体が完了し、監査・再生・記録整合が成立した実モデル記録 |
| 対象 | 適応方式の障害条件、全7設定・各6観測 | 適応方式の全12課題・通常/障害の24セル、各10反復 |
| 成績閾値 | 全設定で成功割合0.80以上 | 全24セルで成功割合0.90以上 |
| 対応した低下 | small・深さ3・sparseからlarge・深さ5・denseへの成功率低下0.10以下 | 適用しない。各課題・条件の成績を個別に判定 |
| 不変条件 | 根・プロトコル・観測した局所比較に違反がない。成功回復の局所比較は非空である | 根・プロトコルに違反がない |
| `PASS` / `FAIL` | 完全で有効な実測で、全基準を満たせばPASS、一つでも満たさなければFAIL | 完全で有効な実測で、全基準を満たせばPASS、一つでも満たさなければFAIL |
| `UNCERTAIN` | simulated、未実行、欠測、無効記録、必要な局所対照なし、閾値の事前固定なし | simulated、未実行、欠測、無効記録、固定反復数や閾値の不備 |

規模設定の6観測に対する0.80は、少なくとも5成功を要する。基準から最大複合負荷への6組では、成功1件の純減が約16.7パーセントポイントになるため、10ポイントの許容値は観測上の純減を許さない。この離散性を隠して連続的な精度があるように扱わない。

規模の対応は課題IDそのものではなく、課題族・分割・元インスタンス・反復番号で付ける。規模設定が変わると課題IDが変わるためである。元成分を共有していても、障害を与える成分が異なる場合がある。したがって最大設定との差は、規模・深さ・依存負荷などが同時に変わる**有限の複合負荷診断**であり、大きさだけの因果効果ではない。

修復へ至らなかった失敗試行も設定別成績の分母に残す。その試行で成果物の局所比較が発生していない場合、保持率100%を与えず、局所性未観測の失敗経路として数える。成功した回復で非空の比較が欠ける場合は規模耐性の判定を保留する。

反復の9/10は、記録された10回に対する達成条件である。「将来の成功確率が90%以上」「任意の課題でも安定」「検出力が十分」という結論ではない。有限基準がPASSでも `sufficiency_status` と `scientific_sufficiency_status` は `UNCERTAIN` を維持する。

## 4. 指標の定義と単位

数値は保存記録からの件数、比率、時間である。下表の変数名は出力フィールドに対応する。構造は `tree`、改訂は `replanning`、成果物局所性は `execution_locality`、依存失効は `dependencies` に保存する。

| 記号・フィールド | 意味（日本語） | 単位（SI） | 定義 | 定義域・前提 | 型 |
|---|---|---|---|---|---|
| `task_clusters` | 区別された課題ID数 | 1、件数 | 同一課題の反復・条件・方式をまとめて数える | 非負。独立性そのものの保証ではない | 整数スカラー |
| `goal_count` | 目標数 | 1、件数 | 根・中間目標・葉の総数 | 再生済み階層から算出。flatの階層比較は対象外 | 整数スカラー |
| `leaf_count` | 葉目標数 | 1、件数 | 実行・公開採点に対応する葉の数 | 認証葉と領域葉を含む | 整数スカラー |
| `max_depth_edges` | 最大階層深さ | 1、辺数 | 根を深さ0とする最長経路 | 要求深さの階層数とは1異なる | 整数スカラー |
| `dependency_edges` | 直接依存辺数 | 1、件数 | 葉に宣言された直接の前提関係の総数 | 循環・重複・存在しない参照を検査済み | 整数スカラー |
| `dependency_density` | 直接依存辺の密度 | 1 | 辺数を、同じ葉数で可能な有向非循環グラフの最大辺数で除した値 | 0から1。葉が2未満なら0 | 実数スカラー |
| `attempted` / `replan_attempts` | 発行した再計画要求数 | 1、回数 | v2では `request_started` の再計画要求を数える | 通信失敗・応答後予算超過も含む。v2の結果と再生測定で同じ境界 | 整数スカラー |
| `accepted` / `rejected` | 受理・拒否した再計画応答数 | 1、回数 | 対応する処理イベント数 | 未完了要求があると両者の合計は要求数に届かない | 整数スカラー |
| `unnecessary` | 規則上不要な再計画要求数 | 1、回数 | 現在の失敗または必要判断を欠く要求 | 意味的・因果的な最適性の判定ではない | 整数スカラー |
| `unrelated_*_checked` | 無関係な対象の比較回数 | 1、比較件数 | 目標または成果物フィールドを実際に比較した総数 | 同じ対象の別イベントでの比較も数える。ゼロは未検証 | 整数スカラー |
| `unrelated_*_unchanged` | 保持された比較対象数 | 1、比較件数 | 比較で等しかった回数 | checkedを超えられない | 整数スカラー |
| `invalidated_goals` / `reverified_goals` | 失効・再検証された完了証拠数 | 1、遷移件数 | 完了から未完了、および新たな検証による完了への遷移 | 異なる時点で同じ葉を再度数えうる | 整数スカラー |
| `wall_seconds` | 試行の実経過時間 | s | ローカルの試行開始から終了まで | クラウド推論だけの時間ではない | 非負実数スカラー |
| `elapsed_seconds` | 論理応答時間 | s | 共有計画を含む論理的な応答時間の総和 | 再利用計画の応答時間も論理計上 | 非負実数スカラー |
| `n_measured` / `n_missing` | 計測済み・未計測の試行数 | 1、件数 | 各指標の分母内で区別した件数 | 未計測をゼロに置き換えない | 整数スカラー |
| `minimum_setting_success` | 規模設定ごとの最低成功割合 | 1 | manifestに固定した0.80 | 実API開始前の設計閾値 | 実数スカラー |
| `maximum_paired_drop` | 対応した最大許容低下 | 1 | 基準成功割合から最大複合負荷成功割合を引いた差に対する上限0.10 | 6組すべて観測。統計的な許容限界ではない | 実数スカラー |
| `minimum_task_condition_success` | 課題・条件ごとの最低成功割合 | 1 | 各10反復に対して固定した0.90 | 全24セルで満たす必要がある | 実数スカラー |
| `u_c` | 合成標準不確かさ | 対象量に依存 | 誤差源の確率モデルと共分散が未定義のため算出しない | 数値を与えない | 未定義 |
| `k` | 拡張係数 | 1 | 本監査では適用しない | 数値を与えない | 未定義 |

**単位確認：** 目標数・辺数・試行数は件数、密度・成功率差は無次元、時間は秒である。これらを足して一つの性能値にしない。例えば根・中間・葉の3階層では、要求深さは3、根からの最大辺深さは2となる。比較件数0に対して保持率100%は定義しない。

費用・時間には中央値、最小・最大、計測件数を付ける。HW、観測できたCPUクロック範囲、バッチサイズは `host.json` の条件を報告へ渡し、未提供なら未提供とする。ローカルCPUを提供者の推論HWと見なさない。トークンは件数であり、そのまま料金を意味しない。

## 5. 判定の読み方と互換性

| 判定 | この9要件表での意味 |
|---|---|
| `PASS` | その行に明記した有限の証拠条件を満たした。方式の普遍的優越性や将来の安定性を認定しない |
| `FAIL` | 観測した違反、またはその行の限定された達成条件の不成立。課題失敗と装置の監査失敗を区別する |
| `UNCERTAIN` | 未実行、欠測、必要な事象が未発生、比較対象が空、モデル実測がない、科学的十分性を定めていない場合 |
| `NOT_APPLICABLE` | flat方式の階層測定など、方式・条件の定義上その操作が対象外。未観測の代用には使わない |

`engineering_status` はoracleでも合格しうる。ただし記録の整合問題がある場合、根などの肯定的なフラグだけで工学的PASSを維持しない。監査の問題件数を報告し、それを実際の根変更件数へ置き換えない。

`empirical_status` は有効な実モデル記録がなければ `UNCERTAIN` とする。R1・R4・R8・R9の総合的な行判定を、シミュレーションだけで実測合格にしない。R8とR9の `status` は3.2節の有限基準を表す。一般的な規模法則・将来安定性・科学的標本十分性の判定は、有限基準のPASSと独立に `UNCERTAIN` のままである。

新しいmanifestは `hiergoal.study.v2` と `evidence_contract="all-nine-v2"` を使う。v2の元studyを判定するには、従来の完全性・方式比較条件に加えて、再生監査、根の保持、成功の独立最終採点が必要である。予算切れによる正当なFAILは、非公開最終採点へ到達していなくてもよい。

解析器はv1記録も読める。v1に新しい機構証拠がない場合、その欄は `UNCERTAIN` とし、古いフラグから補完しない。v1の既存判定アルゴリズムの互換性を保つことと、v1に新しい9要件の証拠があると認めることは異なる。

なお解析器はJSONの整合を検査するだけで、単独ではログファイルを再生しない。実際の収集経路は、先に `audit_trial` でイベント列・成果物・採点結果を再生し、その後に `mechanism_evidence` を付与する。ハッシュ鎖は第三者署名ではなく、記録全体を生成し直せる者による偽造まで防止したとは扱わない。

## 6. H / T / D / C / U

| 項目 | 検証計画 |
|---|---|
| H：反証可能な仮説 | 固定した課題・依存関係・根契約・予算の下で、強制失敗と対象改訂の前後を再生でき、局所修復が無関係な対照を保持する。有限の規模成績0.80以上・低下0.10以下、および各反復セル0.90以上を別に検証する。方式差は元studyの別仮説 |
| T：最小検証 | オフラインの正例・改変負例・未実行・欠測を検査し、各プロファイルの予定行を残す。機構の回復実例は各課題族で必要。反復追加は各10回の固定設計で、良い途中結果による成功停止をしない |
| D：合否条件 | 型・割当て・監査・根・最終採点の不整合は成功根拠から除外する。局所比較は非空で全比較保持が必要。不要要求や上限超過はR6をFAILにする。R8・R9は完全な有効実測でのみ有限基準のPASS/FAILを出し、一般的十分性は保留する |
| C：対立説明・破れ方 | 介入が実体課題を壊していない、無関係な対照が空、改訂文だけ変わった、追加要求が無用、採点器が誤っている、同じ課題の反復で見かけの精度を作った、固定階層でも同じように修復できた |
| U：不確かさ | モデル非決定性、合成課題選定、共有元インスタンス、採点器の妥当性、通信・計測欠測、提供者側のHW・混雑。標本区間を全誤差の合成不確かさと呼ばず、未定義の `u_c` や `k` を数値化しない |

反復数を増やしたことや、有限基準に通ったこと自体を「科学的に十分」と呼ばない。将来の確率的な十分性を判定するなら、許容する母集団の不安定率、必要な区間幅、対象となる課題分布、誤判定の許容度を実測前に追加定義し、別の解析契約として固定する。

## 7. オフラインでの確認

以下はモデル要求を行わないテスト・準備・oracle検査である。保存先は新しいディレクトリを使い、準備後にソースが変わった古いmanifestへ追記しない。

```bash
python -m unittest discover -s tests -v
python -m hiergoal.study prepare --profile mechanism --output runs/requirements-prepared
python -m hiergoal.study check --profile mechanism --output runs/requirements-offline
python -m hiergoal.study check --profile scale --output runs/scale-offline
python -m hiergoal.study check --profile reliability --output runs/reliability-offline
```

調査順は、`manifest.json` の割当て・上限・ソースハッシュ、`results.json` の監査状態、`summary.json` の9要件と分母、必要に応じて `trials/*/trace.jsonl` の該当遷移とする。実APIの開始手順は [実験プロトコル](method_study_ja.md) の別段階に従う。

### ERROR CHECK

- 未実行の予定試行を成功・失敗へ勝手に置き換えない。
- 証拠のない旧フラグ、自己申告、oracleの合格を実モデルの効果にしない。
- 根保持、計画の局所性、成果物の局所性、終端採点を別々に確認する。
- 強制した領域失敗と認証葉の失効、発火なしと無影響を区別する。
- 深さの階層数と辺数、試行数と課題ID数、論理使用量と実要求量を区別する。
- 反復追加や規模の記述結果で、元の216試行の判定条件を変更しない。

## 8. 〈応用・転用例〉

| 関連分野 | 転用できる考え方 | そのままは持ち込めない前提 |
|---|---|---|
| ソフトウェア検証 | 根契約、状態遷移、成果物、採点器の一致を再生で確認し、改変負例で検出能力を試す | 合成課題の採点器が一般のソフトウェア仕様を完全に表現するとは限らない |
| 実験計画・因果推論 | 対応する対照方式、割当て条件の保持、介入後の選別を避ける集計、課題単位の反復管理 | 配信後の回復率だけで方式の因果効果を推定できない |
| 分散処理・データ来歴 | 古い完了証拠の失効、依存先の再検証、実行要求と応答の区別、監査可能なイベント列 | ハッシュ鎖だけで第三者認証や外部サービスの実行事実までは保証できない |
| 信頼性工学 | 全成功・混在・全失敗・未観測を分け、回数だけで安定性を保証しない | 10回の同一課題実行を独立な実世界故障標本とは扱えない |

## 9. 〈次に考える問い〉

**適応方式だけが回復した場合、改善を「失敗の検出」「保存計画の改訂」「単なる追加の修正機会」のどれに帰属させるために、どの対照と追加測定が必要か。** この区別を決めずに、成功ログから再計画の有効性まで結論してはいけない。

### 〈50字超要約〉

9要件を再生可能な証拠と個別の判定へ対応付け、強制失敗・局所保持・規模・反復変動を検査できる設計にする。ただし、オフライン合格を実モデルの優越性へ変換せず、未実測と標本の十分性は未確認のまま明示する。
