# Controlled Recovery Pilot：実行前プロトコル

版：`recovery-v1.0`。設計日：2026-11-27（日本時間）。

## 目的と仮説

同じ失敗後の状態から、失敗したサブゴールの指示を一度修正する手続きが、固定指示による修復に比べて回復を改善するかを測定する装置を構築する。
今回の24試行は装置・会計・天井効果を調べるパイロットであり、有効性を確証する本実験ではない。
実行前にこの文書、実装、評価器、実行条件のSHA-256をmanifestに固定する。

| 区分 | 事前に固定する内容 |
|---|---|
| H：反証可能な問い | 同じ故障後成果物・環境・初期計画から、再計画を含む修復と固定指示の修復に、独立採点の回復結果・費用の違いがあるか |
| T：最小検証 | 3分野×未使用2課題×2反復×2腕＝24割当。6固有課題、12ペア。準備12枠を別に記録 |
| D：装置判定 | 12ペアの開始状態一致、24修復試行の再生監査、終了状態と費用の整合性が揃えば装置PASS。欠測・監査不整合は未完了として報告 |
| D：有効性判定 | 今回は常にUNCERTAIN。将来の本実験候補は改善幅10 percentage points、信頼水準95%。標本数・解析は別途事前固定 |
| C：対立説明 | 課題が容易で両者成功、余分な診断推論の効果、指示修正の失敗、再計画費用による不利益、モデル更新・時間順序、準備成功への条件付け |
| U：不確かさ | 6課題しかなく課題内2反復は独立課題ではない。サンプリングseedはAPI側に固定しない。計測誤差の合成標準不確かさ・包含係数は今回推定しない。未観測API使用量はnull |

## 比較と準備

- A `fixed`：元の階層・葉の指示を保持して修復する。
- B `adaptive`：故障直後に対象葉の指示修正を一度試み、その後修復する。修正が拒否されても再試行せず、元の計画で修復する。
- 両腕とも既存成果物フィールドを変更できる。局所性はフィールドアクセスの禁止で作り込まず、実際の変更を記録して検証する。
- Bの診断・指示修正リクエストは、Bの呼出し数・tokens・時間に含む。指示書換え単独の効果と追加診断推論の効果は分離しない。

各ペアは、モデルによる初期計画1回と、公開フィードバックだけを用いるflatな成果物生成から始める。
この準備はA/Bから独立した共有段階で、費用は一度だけ別会計にする。初期計画はowner指定の階層・依存関係に対する葉の指示のみ。
公開採点を通った成果物を非公開評価器でも採点し、双方を通ったときだけ故障注入する。非公開採点の不合格をモデルへ返して修正を続けない。
計画不正、予算超過、非公開採点不合格などの準備失敗は保存し、対応するA/Bを`NOT_RUN_SOURCE_FAILURE`として残す。引き直し・代替課題・有利な状態の選別をしない。

既存の決定的`forced_subgoal`故障を用いる。コード式は指定式を`0`に、データ変換は所定レコードの整数金額を1だけ変更し、スケジュールは所定ジョブの開始時刻を-1にする。
実質的なdomain gateの合格から不合格への変化と、環境が変わらないことを確認する。
正解を生成する`reference_solution()`はオフライン模擬応答にしか使わない。

故障後成果物・環境・最上位契約・初期計画・公開採点・空の履歴を複製する。
故障前の成果物、準備中の応答履歴、非公開採点、故障receiptは修復モデルに渡さない。
監査用checkpointにはそれらを保存し、モデル入力は許可された故障後情報から再構築する。
採点器をエージェントに変更させず、成功申告を採点に使わない。

## 課題・割当

既存のコード式修復、整数金額のデータ変換、資源制約スケジューリングを使用する。
ScaleTaskのsmall・depth 3・sparseを固定し、独立2コンポーネントを含める。
新しいtask seed `20261127`、instance 0と1を使用する。18個の既存manifestに対しtask ID、root・公開仕様・初期環境の指紋の非重複を確認する。同じ課題族・故障方式であることは変わらない。
ペア順序はseed `20261127`で事前に並べ替える。腕順序はfixed先行6組、adaptive先行6組になるよう並べ替える。

## 環境と予算

| パラメータ | 値 | 定義・単位・型 |
|---|---:|---|
| 固有課題数 | 6 | 3課題族×2 instance。無次元の整数 |
| 課題内反復 | 2 | task内容を共有する別モデル生成・修復。無次元の整数 |
| 準備枠・修復枠 | 12・24 | 別会計のフェーズ数。無次元の整数 |
| モデル・reasoning | `gpt-6-luna`・`low` | OpenAI Responses、直接endpoint。文字列 |
| 最大呼出し | 各フェーズ8 | 計画・拒否・未知の送信を含む。全体最大288。無次元の整数 |
| token停止閾値 | 各フェーズ64,000 | 入出力の合計。応答後の実測。無次元の整数カウント |
| 最大出力 | 4,096 tokens | 残りtoken予算が少なければ縮小。無次元の整数カウント |
| 最大論理payload | 48,000 bytes | UTF-8 JSONのオクテット数。整数。API wire変換の指紋も保存 |
| リクエストtimeout | 90 s | API応答待ち。時間のスカラー |
| フェーズ停止時間 | 600 s | 単調時計の経過時間。時間のスカラー |
| 全体の開始停止閾値 | 14,400 s | 準備・修復・監査を含む経過時間。次のフェーズを始める前に検査。時間のスカラー |
| 同時実行数 | 1 | 逐次・batch 1。無次元の整数 |
| 再計画回数 | B最大1、A・準備0 | 拒否も一回を消費。無次元の整数 |

単位確認：準備12枠と修復24枠は同じ呼出し上限を持ち、36フェーズで最大288リクエストとなる。時間は秒で統一する。token数とbyte数は別測定で、相互に同一視しない。
64,000 tokensは厳密な請求上限ではない。入力使用量を応答後に知るため、最後の応答で超える場合がある。超過応答は費用に含め、成果物や計画には適用せず、予算超過FAILとする。
超過を成功に数えず、実測量を残す。実際の料金をtokensから推定した料金と混同しない。
ローカル評価器はPython 3.11以降・標準ライブラリ。CPU、観測クロック、Python版、commit、batchをhost.jsonに記録する。推論側ハードウェアはprovider管理で観測不可。

## 停止と再生監査

HTTP・transportエラーは自動再試行しない。使用量が不明なら総量nullと既知部分を両方残し、リクエスト試行は数える。
transport・装置例外・再生監査失敗は全体停止。通常の準備・修復FAILは結果として残し、次の割当へ進む。
時間は停止閾値である。フェーズ内は各送信前と応答後、全体は各フェーズ開始前に検査する。進行中リクエストや進行中フェーズを閾値時刻に強制終了する設計ではなく、その分の超過を経過時間として残す。workflow自体の上限は260分。
各フェーズ後に、ハッシュ鎖、開始状態、実際の入力、応答JSON、パッチ、指示差分、拒否、状態遷移、公開・非公開採点、費用、終了理由を再構築する。
未実施枠をFAILとみなさず、欠測・準備失敗・全体停止を区別する。
処理済みoutputへの再実行は拒否し、既存結果に継ぎ足して成功まで走らせない。

## 報告

準備成功数／12、割当24枠の実施状況、監査結果、ペア別4分類（両者成功・Bのみ成功・Aのみ成功・両者失敗）を報告する。
各腕・課題族の回復数、呼出し・tokens・時間の中央値と範囲、再計画の試行・受理・拒否、無関係なフィールドの各段階の変化を示す。
主比較は準備成功状態に条件づけた回復で、準備費用・準備成功率も併記する。
全ペア同一結果から退化したbootstrap区間を提示しない。固定指示が全成功なら天井効果を明記する。
最上位契約の保持はホストの強制と記録による観測で、一般的な意味での目的維持能力の証明ではない。
大規模化、正常時の再計画不要判断、階層再構造化、Hermes統合、9要件すべての再検証は今回の対象外である。

## 実行と明示的な起動

```bash
python3 -m unittest discover -s tests -p 'test_controlled_recovery*.py' -v
python3 -m hiergoal.recovery check --output runs/recovery-check
python3 -m hiergoal.recovery prepare --output runs/controlled-recovery
python3 -m hiergoal.recovery run --output runs/controlled-recovery --execute --approve-paid-api
python3 -m hiergoal.recovery collect --output runs/controlled-recovery
```

`prepare`・`check`・`collect`はAPI推論をしない。`check`は模擬応答による装置検証と明示する。
既存v2.5 workflow・有料実行フラグ・記録は変更しない。
新workflowは手動の明示的run、またはユーザーの「構築して実験までしてください」に対応した一度限りの起動依頼ファイルの追加のみ実モデル実行を認める。
後者は実装commit・protocol指紋・予算・24割当との一致、main、実行者、初回attemptを検査する。通常の実装や文書更新で推論を開始しない。
原記録は実行run/attemptごとに独立保存する。将来の変更で既存manifestや結果を書き換えない。

## 関連分野

- AI計画：失敗した葉の局所修正と固定計画の比較。
- 制御・障害回復：同じ故障状態を復元し、無関係な状態への影響を測る。
- 因果実験設計：共有checkpointによる対応比較、課題内依存、欠測、準備成功への条件付けを区別する。
