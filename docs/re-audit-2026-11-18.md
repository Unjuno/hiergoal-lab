## Concrete audit findings / repairs

| Severity | Finding | Resolution |
|---|---|---|
| High | After replanning failed leaf S1, downstream S2/S3 could remain `completed` without re-evaluating their evidence, violating dependency semantics | Invalidate all transitive dependents and expire the impacted parents' verification state. Repeat fixed gates on each dependent before restoring completion |
| High | The public report could mark `PASS` while parent gate files or leaf gate evidence were missing, based only on final overall tests | Require per-parent and per-leaf gate JSON, matching counts and complete acceptance-gate coverage before treating `PASS` as substantiated |
| Medium | No integrated test exercised regression detected at a parent after individual leaves had passed | Added a fake-Hermes regression test that damages an earlier gate during a later execution; verifies localized replan, transitive revalidation and eventual acceptance |
| High / outstanding | The experiment's goal graph and scheduler live in a separate Python harness, not Hermes' own native goal persistence or Kanban execution ledger | Still not implemented upstream, and must not be reported as completed |
| High / outstanding | No real Hermes + Luna end-to-end run, no verified account credentials, no actual invoices; host shell/file tools are not OS-sandboxed | User must execute locally in a disposable environment; billing guard is a rough soft limit only |
| Scientific limitation | One fixed task without flat-goal comparison does not estimate causal improvements from hierarchy or replanning | Report as a single-case functionality observation, not a performance superiority claim |

## Criteria for publishing a future live result

1. Capture Hermes and Python versions, the exact Git commit, task fixture hash and the selected provider/model.
2. Show an actual Hermes `stream-json` trail including tool calls, not only a written plan.
3. Verify each short-term gate and parent acceptance independently; preserve an uninterrupted evidence chain when reporting PASS.
4. Distinguish planned actions, executed actions, passed gates, regressions, replans and skipped/preverified leaves.
5. Compare the token estimate against actual OpenAI usage; do not describe the $3 soft stop as a billing cap.
6. Review/redact logs and workspaces before posting any research result to the upstream issue.
